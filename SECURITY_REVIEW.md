# Security and publication review

## Public data boundary

The repository contains synthetic booking and financial records only. It does not include operational databases, customer workbooks, generated business exports, logs, credentials, or organization-specific branding.

## Implemented controls

- Synthetic marine-tour data and generic company names only.
- No hard-coded credentials or API keys.
- Runtime configuration through environment variables.
- Secret key generated by the hosting blueprint.
- CSRF validation for every POST form.
- Five-megabyte upload limit and explicit XLSX/CSV allowlist.
- XLSX signature and expanded-archive-size checks.
- Ten-thousand-row processing limit per source.
- Row-level type and required-field validation.
- No raw workbook persistence.
- Stored normalized results expire after 24 hours by default.
- Parameterized SQLite queries.
- Spreadsheet formula-injection protection in exported text fields.
- CSP, frame denial, MIME sniffing prevention, no-referrer policy, secure-cookie option, and no-store headers for results.
- Non-root Docker runtime.
- Git ignore policy for databases, logs, environment files, uploads, exports, and ad hoc spreadsheets.
- Automated source security gate in GitHub Actions.

## Residual risks

- The public demo has no authentication or user isolation.
- SQLite is process-local and is not suitable for multiple instances or sustained concurrent workloads.
- Results are not encrypted at the application layer.
- Uploaded files are parsed in the request process; a production service should use isolated background workers and malware scanning.
- Company aliases are configured in code for the demo.
- Dependency and container vulnerability scanning should be added to a production release process.

## Publication decision

The demo is suitable for a public portfolio when the security gate and test suite pass. It is not approved for confidential production data.
